# ADR-0005 — Internationalisation: i18next + expo-localization

**Status:** Accepted
**Date:** 2026-04-21
**Deciders:** Solo founder

## Context

Ludi is bilingual from day one: English and Greek. This is a hard requirement for Cypriot users — roughly 50% prefer Greek for app UI, and a Greek-only or English-only app halves the addressable market.

The copy is not an afterthought: it's in the design prototype (`COPY.en` and `COPY.gr` objects). Translators are non-devs — the format needs to be editable without touching TypeScript.

Requirements:
- Automatic locale detection from device settings.
- User override that persists across app launches.
- Interpolation (`"{{count}} open matches"`) and pluralisation (Greek has singular/plural/neuter rules).
- No runtime cost for users of a single locale.
- Type-safe translation keys (missing-key errors at compile time, not runtime).

## Decision

Use **i18next** + **react-i18next** bindings, with **expo-localization** for device locale detection. Persist the user's locale override in `AsyncStorage` under `ludi.locale`.

- Translation resources live in `@ludi/ui/src/copy.ts` for MVP (co-located with design system).
- When copy volume grows (~100+ keys), extract to JSON files in `@ludi/i18n/locales/{en,gr}.json` — stub package already scaffolded.
- Translation keys are strongly typed via the `Copy` interface in `copy.ts`.
- Bootstrapping happens in `apps/mobile/src/lib/i18n.ts`, awaited by the root layout before rendering UI.

## Consequences

### Positive
- i18next is the de-facto React i18n library; extensive docs, active community, works with RN.
- expo-localization auto-detects `en` / `el` / `gr` and maps `el` → `gr` (Greek locale code on iOS is `el`, we use `gr` for legacy reasons).
- Structured translations support ICU-style pluralisation when we need it.
- JSON locale files are editable in any translation management tool (Lokalise, Crowdin) when we hire translators.
- Strong TypeScript integration: `t('greet')` is auto-completed; typos caught at build time.

### Negative
- `returnObjects: true` for array copy (`cities`, `filters`) bypasses type safety a bit; manageable with assertions.
- Bundle size: +~15KB gzipped for i18next core. Negligible.
- Server-side (Edge Functions) needs its own i18n if we want translated emails. Plan: pass `locale` param, use a lightweight lookup table, not full i18next.

### Neutral
- Locale override UI lives on the Profile screen (MVP); a quick-toggle in the app chrome can be added later.

## Alternatives considered

### React Intl (FormatJS)
Excellent ICU support, Unicode-correct. Rejected: heavier API surface than i18next for our needs; weaker RN ecosystem docs.

### react-native-localize + custom lookup
Zero-dependency, minimal. Rejected: we'd rebuild interpolation, pluralisation, fallbacks. Reinventing the wheel.

### LinguiJS
Compile-time extraction, smaller runtime. Rejected: smaller community, lower RN community velocity; the extract/compile step adds CI complexity not worth it at our scale.

### Hard-coded two maps (COPY.en, COPY.gr) with a `useLocale()` hook
What the prototype does. Rejected for production: no pluralisation, no interpolation, no fallback, no lazy loading, no translator-friendly format. Fine for a prototype, unscalable.

## Follow-ups

- When we hire our first translator, split `copy.ts` into `en.json` and `gr.json` under `packages/i18n/locales/`.
- Write a script to flag missing GR translations in CI (`i18next-scanner` or custom).
- Edit messaging for Greek pluralisation needs validation with a native speaker — the prototype's current strings have not been professionally reviewed.
- Consider adding a `locale` column to `users` for server-side email content (auth emails, booking confirmations).
